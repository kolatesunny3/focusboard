# agents.md — FocusBoard

Working agreement for AI coding agents (and humans) in this repo.
`features.md` describes **what** to build. This file describes **how**.

## Project

FocusBoard is a lightweight Windows desktop task planner.
A task = title + description + any user-defined attributes ("fields").
Dropdown lists are reusable masters defined in Settings.
All data lives in plain JSON files under `%LOCALAPPDATA%\FocusBoard\`.

No database, no webview, no network, no telemetry, no background services.

Status: MVP implemented (all build phases below). Phase 0 budgets measured — see
the Budgets table.

## Stack

| Concern | Choice |
|---|---|
| Language | Rust (edition 2024, latest stable) |
| UI | Slint — `fluent` style pinned in `build.rs`, exact version pinned in `Cargo.toml` |
| UI compile | `slint-build` in `build.rs`, `slint::include_modules!()` |
| State | Plain Rust structs + Slint models (`VecModel<T>`, `ModelRc`) |
| JSON | `serde` + `serde_json` (pretty-printed) |
| Dates | `chrono` |
| Dialogs | `rfd` (folder picker, fatal error dialogs) |
| Single instance | `single-instance` |
| Tests | built-in `#[cfg(test)]` |

Slint is compiled with `default-features = false` and exactly four features:
`std`, `backend-winit`, `renderer-software`, `compat-1-18`. The femtoVG (OpenGL)
renderer, accessibility (AccessKit) and the system tray are deliberately **not**
built in — that is worth ~2.5 MB of binary and a lot of idle RAM. Add one back
only with a measured reason.

Do not add dependencies without a concrete need. No async runtime, no ORM, no
logging framework, no error-handling framework.

## Architecture rules

- `.slint` files do presentation and callbacks only. No business logic there.
- Rust owns all state. UI reads Slint models; edits come back through callbacks.
- Field kind ints (0..7) exist only in `values.rs`. They are never stored in
  JSON — files store type names like `"date"`, `"select"`.
- `values.rs` is the single place that encodes, decodes, and validates a value.
- `storage.rs` functions take a data root `&Path` parameter so tests can point at
  a temp dir. Tests must never touch the real user data folder.
- Autosave: 700 ms debounce via `slint::Timer`; flush pending writes in
  `on_close_requested` before the window closes.
- No `unwrap()` / `expect()` on IO or parsing paths. Errors surface to the user.
- Fatal startup errors (data unreadable): show an `rfd` message dialog with the
  file path and backups location, then exit. Never overwrite or reset on error.
- Keep `app.rs` moderate: if it starts mixing UI and storage logic, extract a
  module rather than letting it grow into a god file.

## Storage rules (do not break)

Four files in `%LOCALAPPDATA%\FocusBoard\`:

| File | Contents |
|---|---|
| `lists.json` | dropdown masters + options |
| `fields.json` | field definitions |
| `tasks.json` | tasks with their `values` map |
| `settings.json` | theme, window size/position (physical pixels) |

Plus `<name>.json.bak` (previous good write, per file) and
`backups/YYYY-MM-DD-HHMM/` (daily snapshot, keep the last 7).

1. Entity files: `{ "schemaVersion": N, "items": [...] }`; `settings.json` is a
   flat object with its own `schemaVersion`.
2. Save order: lists → fields → tasks → settings. Only changed files are written.
3. Atomic write: write `<file>.json.tmp`, sync, rename over the original; keep
   the previous content as `<file>.json.bak`. Retry a few times on sharing
   violations (antivirus scanners can hold the file briefly).
4. Load: parse the main file; on failure try its `.bak`; on failure stop with a
   dialog. Never silently start empty.
5. Tolerant loading: task values referencing missing fields/options are kept and
   rendered as "(missing)". Deleting a field or list runs a cleanup pass that
   removes its references and rewrites `tasks.json`.
6. `schemaVersion` older than the app: back up the whole folder, migrate, save.
   Newer than the app: refuse to open (data came from a newer version).
7. Only one instance may run (`single-instance`).
8. Export/Import = copy/restore the four files via folder picker. Import backs up
   the current files before replacing them.

Short rationale: separate files mean there is no cross-file transaction, so
dependency-ordered saves plus tolerant loading are the consistency strategy.

## Window behaviour

- Size/position are stored in **physical pixels** (what the windowing system
  reports) and restored from `settings.json`.
- Restore clamps size and position to the primary monitor's work area
  (`SystemParametersInfoW` via a small `unsafe extern` declaration — no extra
  crate), so a window saved on a now-disconnected monitor cannot come back
  off-screen.
- First run (no saved position): the window is centred on the work area.
- Maximized state is restored too (`Window::is_maximized`/`set_maximized`). While
  the window is maximized the capture keeps the previous *restored* geometry, so
  un-maximizing after a restart lands on a sensible size instead of screen-sized.
- The size must be applied **after** `ui.show()`: the initial layout pass
  overwrites `set_size()` calls made before the window exists.
- `ui/app.slint` sets `min-width: 830px`, `min-height: 520px` (logical). The width
  keeps the task table usable; the height keeps the built-in date-picker popup
  (calendar + its OK/Cancel row) inside the window — in a shorter window the popup
  is clipped and the date can never be confirmed.
- Slint renders popups inside the main window, so popup content must fit the
  window: check every popup at the minimum window size.

## Grid (tasks table)

- Column geometry is explicit and shared: `Theme.grid-unit`, `Theme.grid-x` and
  `Theme.grid-width` in `ui/theme.slint` turn a total width and a column count into
  an x/width pair (title 5 units, each custom column 2, 8 px padding, 6 px gaps).
  The header and `NavRow` both call those functions, so a column cannot drift away
  from its heading. Never go back to letting a layout distribute the columns.
- Why the explicit maths: Slint derives an element's layout info from its children
  (`passes/default_geometry.rs`, children without explicit `x`/`y`), so a plain
  `Rectangle` containing `Text` reports a *content-based* preferred width. Layouts
  use that preferred width as the flex basis and only distribute the surplus by
  `horizontal-stretch` — the header and each row then base their columns on
  different content and nothing lines up. Columns therefore set `x` and `width`
  themselves and sit outside any layout.
- Text inside a column sets `width`/`height` to `parent.*` (or to the column width
  minus the space a tag needs), which is what makes `overflow: elide` work. Cells
  also set `clip: true` so a very long value is cut at the column edge.
- Dropdown values render as `Chip` (rounded tint from the option colour, themed
  alpha for light/dark), inside a cell-local `HorizontalLayout` whose trailing
  spacer keeps the chip at its natural width and left aligned.
- The "archived" marker lives inside the title column, so archived rows keep the
  same columns as the header.
- Order: `SortField::Manual` is the default and keeps the stored order (the order
  rows were dragged into). A header click cycles ascending → descending → manual.
- Drag & drop lives in `NavRow`: its `TouchArea` uses `pointer-event`, because
  `clicked` cannot tell a click from a drag. Moving more than 4 px turns the press
  into a drag (`drag-start`/`drag-move`/`drag-end`, plus `drag-cancel` for a
  cancelled gesture); anything less stays a click and calls `pick`, which selects
  the row. The page holds `drag-from`/`drop-index` and draws the drop line +
  dimmed row. The drop index is the travelled distance divided by
  `Theme.row-height` (rows sit flush, so the pitch is the row height), which keeps
  scrolling out of the maths.
- `App::move_task` reorders the ids of the rows currently on screen
  (`table::reorder`) and writes them back into the slots those rows occupy in
  `tasks.json` (`table::apply_order`), so rows hidden by a search or filter keep
  their place; then it switches the sort to manual.

## Look and feel

- The product logo is `fb.png` (root). `ui/app.slint` embeds it as the window
  `icon` and in the expanded sidebar; `build.rs` links `icon.rc` (compiled from
  `fb.ico` by MinGW `windres`) into the exe so Explorer and the taskbar show it
  too. Regenerate the ICO with `tools/make_icon.ps1` after changing the PNG.
- The sidebar collapses to 68 px via the «/» button: labels give way to T/S
  glyphs and the status line is hidden. `AppWindow.sidebar-collapsed` is driven
  from `Settings.sidebar_collapsed` (a `#[serde(default)]` field, so old
  `settings.json` files load unchanged); the callback marks settings dirty and
  the usual 700 ms debounce persists it. Default is expanded.
- `ui/theme.slint` owns every colour: surfaces (`app-bg`, `surface`, `surface-2`,
  `hover`), lines (`border`, `hairline`), text (`text`, `muted`), accent
  (`accent`, `accent-hover`, `accent-soft`, `on-accent`) and status (`danger`,
  `danger-soft`, `success`). Pages use those tokens, never `Palette` directly;
  the fluent std widgets (LineEdit, ComboBox, CheckBox, Button, ScrollView, date
  picker) keep their own palette and sit on top of the themed surfaces.
- Each token is a light/dark pair selected by `Theme.dark`. That flag reads
  `Palette.color-scheme`, so `apply-scheme` must be called with a *resolved*
  value: `App::apply_theme` turns "follow system" into light or dark by reading
  `AppsUseLightTheme` from the registry (`system_prefers_dark` in `app.rs`,
  advapi32 `RegGetValueW`, no extra crate). Slint does not expose the system
  scheme to app `.slint` files (`SlintInternal` is only visible to its own
  styles), and picking a value in Rust keeps the window chrome, std widgets and
  the custom colours consistent. Consequence: an OS theme switch while the app is
  running is picked up on the next start (or on a theme change in Settings).
- Shared controls live in `ui/widgets/controls.slint`: `AppButton`
  (`primary`/`danger`/`quiet`) and `Chip` are components whose root is a
  `Rectangle` with an inner layout, which gives them a content-based preferred
  size inside layouts — do not rebuild them as bare Rectangles. Both keep 2–4 px
  of extra right padding: Slint's elide check is a hair stricter than the
  preferred width it reports, so a tight button renders "Open data fol…".
- Surplus space: a layout hands what is left to children that claim
  `vertical-stretch`, and the fluent `LineEdit`/`TextEdit` claim it. Two
  consequences worth keeping in mind when a form looks bloated:
  - The editor's title and description set an explicit `height` (36 / 120 px);
    without it the title box eats the panel's surplus and grows to ~120 px.
  - A `ScrollView`'s content layout gives its own surplus to its children, so a
    short list of rows or cards stretches them. End the content with
    `Rectangle { vertical-stretch: 1 }` (editor fields, filters, settings lists
    and data tabs) so the rows keep their natural height.
- The modal card has a fixed height (`modal-height`), so the field form keeps
  constant-height slots for the locked-type hint and the error line and the type
  combo raises/lowers the height when it shows the dropdown-list picker
  (310 px, 365 px with the picker). Without that the error line would push the
  buttons out of the card. The task form uses 520 px, capped at
  `root.height - 40px` so it still fits the minimum window.

## Task form (draft edits)

- Both "New task" and clicking a row open modal kind 3 (`ui/widgets/task_form.slint`).
  The form never edits stored data: every callback writes to `App::draft`
  (`Draft { task, editing_id }`), and `rebuild_editor` rebuilds the form from that
  clone. `save_task_form` is the only place that copies title, description and
  values into `data.tasks` (and sets `updated_at`); Cancel/Close drops the draft.
  Quick-add is deliberately unaffected — it still creates a titled task from the
  toolbar in one keystroke.
- Save validates a non-empty title, required fields and `values::validate` before
  committing; errors go into `modal-error` (a fixed-height slot in the form).
- Single-select fields render as a `ComboBox`: `FieldRow.options` is a model with
  "Choose…" at index 0 followed by the option labels, and `select_option` maps the
  chosen index back to an option id through `field_picker_options`. Multiselect
  still uses the checkbox picker and date fields the calendar picker, and both
  write to the draft as well.
- Archive/Restore/Delete are only shown when `task-form-editing` is set, because
  they act on the stored task, not the draft.

## Conventions

- IDs: UUID v4 strings. Timestamps: ISO 8601 UTC.
- `date` values: `YYYY-MM-DD`, no timezone conversion.
- Errors: one small `Error` type implementing `Display`; messages must be
  actionable (say which file, what to try).
- Crate/binary name `focusboard`; product name "FocusBoard".
- UI strings: English, sentence case.

## Testing

Unit tests are required for:
- storage: round-trip, `.bak` fallback, dangling-reference tolerance, migration
- values: encode/decode/validate for every field type
- table: sort comparators, filter predicates, manual-order reorder

`cargo test` and `cargo clippy --all-targets -- -D warnings` must pass before a
phase is done. UI is verified manually:

1. Launch, create a task (New task → fill → Save), quit, relaunch — data persists.
   Check that opening the form and pressing Cancel creates nothing, and that Save
   with an empty title is rejected.
2. Add a field, use it, show it as a column, filter by it. Click a row to edit and
   confirm Cancel leaves the table untouched; single-select fields should be
   inline dropdowns.
3. Archive a field, confirm it disappears from the form but values survive.
4. Corrupt `tasks.json` by hand — app offers the `.bak` instead of crashing.
5. Start a second instance — it must not run concurrently.
6. Move/resize the window, close, relaunch — geometry comes back; maximize first and it
   reopens maximized, with un-maximizing falling back to the last restored size.
7. Drag a row onto another one — the slot is marked, the order survives a restart,
   and a column sort that was active is replaced by the manual order.

When driving the UI programmatically (no human at the keyboard), three rules:

- Send input with Win32 `PostMessage` addressed to the app's HWND. Never use
  `SendKeys` or `SetForegroundWindow`: keystrokes go to whatever window happens
  to be focused, which can be the user's terminal or editor.
- Capture the window with `PrintWindow(..., PW_RENDERFULLCONTENT)` rather than
  grabbing the screen, and make the helper process per-monitor DPI aware
  (`SetProcessDpiAwarenessContext(-4)`). Without that, all coordinates come back
  virtualized (150% scaling looks like 100%) and clicks and captures land in the
  wrong place.
- Check the binary's timestamp before trusting what it does. `target/debug/focusboard.exe`
  silently lags behind `.slint`/`.rs` edits; driving a stale exe wastes a debugging round
  (a fixed empty-state message still looked broken because the running debug build dated
  from before the fix). Either rebuild first or drive the release binary — that one is what
  ships anyway.
- Expect interference on a shared machine: the user clicking the app while a scripted run
  is between commands can create or delete rows (a "ghost task" that appeared and vanished
  was exactly that). Verify against a controlled capture sequence before calling it a bug.
- A drag needs modelled moves: post `WM_LBUTTONDOWN`, then several `WM_MOUSEMOVE` with
  `MK_LBUTTON` set, and only then `WM_LBUTTONUP`. A single jump from press to release is
  a click — Slint's 4 px threshold never sees a move. `fb-msg.ps1 -Action drag -X .. -Y ..
  -X2 .. -Y2 ..` does this (`-Hold` stops mid-gesture so the drop marker can be captured,
  finish with `-Action mouseup`); write the target as `-Y2:163`, since a bare `-Y2 163`
  binds `-Y` twice.
- Column alignment can be checked without eyeballing a screenshot: scan the capture for
  the text runs of the header band and of two row bands (`fb-scan.ps1`-style helper) and
  compare the x starts; a column that moves per row is a layout-basis bug (see Grid).
  For a structural check, temporarily give the header and row columns tinted
  backgrounds, capture, and confirm the bands share edges — remove the tints before
  shipping.

## Known ceilings (deliberate — revisit only when measured)

- Whole-file JSON rewrites; comfortable into the thousands of tasks. Split files
  or reconsider storage only if writes get slow or files reach tens of MB.
- No automated UI tests.
- Accessibility (AccessKit) is not compiled in: the Slint feature is off to keep
  the binary and RAM small. Needed for a public release (see roadmap).
- Slint licensing (GPLv3 / commercial, with a royalty-free desktop tier under
  conditions) must be resolved before distributing closed-source.

## Never do this

- Never add SQLite, any database, a webview, or network calls.
- Never store field-kind ints in JSON; store type names.
- Never delete, overwrite, or "reset" user data because of an error.
- Never write to the real data folder from tests.
- Never put business logic in `.slint` files or let `app.rs` become a god file.

## Budget results

Measured on this machine (Windows, 1920×1080 @ 150% DPI, Rust 1.99.1
`stable-x86_64-pc-windows-gnu`, MinGW-w64 GCC 16.2 linker) on the release artefact:

| Metric | Target | Measured | Verdict |
|---|---|---|---|
| Release exe | ≤ 8 MB | 9.75 MB (10,227,200 bytes) | **over** (see below) |
| Cold start | ≤ 200 ms | 170 ms median over 5 warm launches (139–191 ms) | met |
| Idle RAM | ≤ 80 MB | 31.5 MB working set, 13 MB private | met |

"Cold start" = launch → main window visible, timed by a harness that launches the exe
five times in one process and polls for the HWND every 2 ms; the median is the number.
Do not time it with `Start-Process` plus a 5 ms loop started from a fresh PowerShell
each run: that harness overhead adds 30–300 ms and made this same binary look like
198–480 ms. Either way the first launch after a link is slower, because Defender scans
the freshly written exe. Idle RAM is `WorkingSet64`/`PrivateMemorySize64` read three
seconds after the window appears.

Where the 9.75 MB goes, and what was already removed:

- The full-featured build (default Slint features: femtoVG renderer, accessibility,
  tray) was 11.0 MB and 119 MB RAM. Dropping those got to 9.4 MB / 30 MB.
- Section split: `.text` 4.6 MB, `.rdata` 4.9 MB. `.rdata` is mostly the text stack's
  embedded Unicode data: Slint 1.18 lays out text with `parley`, which pulls the
  ICU4X segmentation dictionaries (CJK, Thai, Khmer, Burmese, Lao — verified present
  in the binary with `strings`) plus `icu_normalizer` / `icu_properties` and their
  `*_data` tables. `parley` exposes no feature to disable them, so this cannot be
  trimmed without vendoring and patching the crate.
- The rest is Slint core + `backend-winit` + software renderer + fluent std-widgets,
  the font stack (`fontique`, `read-fonts`, `swash`, `harfrust`), serde_json, chrono,
  rfd, uuid, and the app itself.
- The exe is self-contained: `objdump -p` shows Windows system DLLs only, so no
  MinGW runtime DLL has to ship next to it.

Levers left, if 8 MB ever becomes hard (each costs functionality or maintenance):

| Lever | Est. saving | Cost |
|---|---|---|
| Replace `rfd` with raw `IFileDialog` COM FFI | ~0.2–0.4 MB | ~150 lines of hand-written unsafe dialog code |
| Replace `uuid` with a hand-rolled id generator | ~0.1 MB | custom id format in the data files |
| Vendor `parley`/`fontique` without ICU | ~1 MB | a fork to maintain; CJK/Thai line breaking falls back to a simpler algorithm |
| `-C force-unwind-tables=no` | ~0.3 MB | C++ exceptions from system APIs could no longer unwind through Rust frames |

Decision (2026-10-19): keep 9.4 MB. The 8 MB target predates knowing the weight of
Slint's text stack, and the number already beats every realistic alternative. Revisit
the rfd/uuid levers only if the app is ever published.
